# Authentication System — smart-ecommerce-jpa

This document describes the entire authentication system implemented in this repository. It covers components, request flows, token formats, headers, configuration, examples, and recommended next steps.

> Location of core files (quick reference)
- `src/main/java/com/miracle/smart_ecommerce_jpa/domain/auth/controller/AuthController.java` — login & register endpoints (returns auth token)
- `src/main/java/com/miracle/smart_ecommerce_jpa/domain/auth/service/AuthService.java` and `AuthServiceImpl.java` — credential verification
- `src/main/java/com/miracle/smart_ecommerce_jpa/domain/auth/service/TokenService.java` — token abstraction
- `src/main/java/com/miracle/smart_ecommerce_jpa/domain/auth/service/impl/SimpleTokenService.java` — current token implementation (simple deterministic token)
- `src/main/java/com/miracle/smart_ecommerce_jpa/domain/auth/filter/SimpleAuthFilter.java` — request filter that authenticates incoming requests
- `src/main/java/com/miracle/smart_ecommerce_jpa/domain/auth/dto/AuthResponse.java` — auth response DTO (includes `token`)
- `src/main/java/com/miracle/smart_ecommerce_jpa/domain/user` — user entity/repository used during auth


## High-level design

- Authentication is handled by the `AuthController` endpoints. Successful authentication or registration returns an `AuthResponse` which contains `userId`, `role`, and a `token` string.
- The token is a simple, custom token (not JWT) generated by the configured `TokenService` implementation. By default the repository contains a `SimpleTokenService` implementation that is deterministic (see Token format section).
- Each incoming HTTP request passes through `SimpleAuthFilter` (a `OncePerRequestFilter`) which attempts to authenticate the request using headers:
  - Primary: `X-Auth-Token` — validated by `TokenService.validateToken(...)`.
  - Fallback: `X-User-Id` — used for development convenience (the filter will look up the user in the DB and set the same MDC values).
- When authenticated, the filter writes `userId` and `userRole` to the logging MDC (Mapped Diagnostic Context) keys `userId` and `userRole`, so downstream code can read these values.


## Login / Registration flow (end-to-end)

1. Client calls `/api/auth/authenticate` (POST) with payload {"email":..., "password":...}.
2. `AuthController` -> `AuthService.authenticate(email,password)`:
   - Look up user by email (UserRepository).
   - Verify password via `PasswordEncoder.matches`.
   - Check user active flag. Return `AuthResponse` containing userId and role.
3. `AuthController` generates token using `TokenService.generateToken(userId, role)`, sets `AuthResponse.token` and returns the response wrapped in `ApiResponse`.

Registration (`/api/auth/register`) follows a similar pattern: create user, then issue a token.


## Request authentication (filter logic)

`SimpleAuthFilter` handles authentication for incoming requests:

- If the request URI is a public endpoint (by default the filter treats certain URI prefixes as public, e.g. `/api/products`, `/api/categories`, `/api/auth`, `/api/health`, and swagger endpoints), the filter skips auth.
- Otherwise, the filter first checks for header `X-Auth-Token`:
  - If present: calls `TokenService.validateToken(token)`.
    - If valid: obtains `AuthPrincipal {userId, role}` and sets `MDC.put("userId", userId)` and `MDC.put("userRole", role)`.
    - If invalid: leaves the request unauthenticated (controller/service should return 401/403 if required).
- If `X-Auth-Token` absent or invalid, the filter checks header `X-User-Id`:
  - If present: parses the UUID, looks up the user in the DB, and (if found) sets MDC values `userId`, `userRole`.
  - If missing/invalid: request remains unauthenticated.
- The MDC is always cleared in a finally block to avoid leaking context across requests.

Downstream code (controllers, services, aspects) can get the current authenticated user via `MDC.get("userId")` and `MDC.get("userRole")`.


## Token format (SimpleTokenService)

The repository currently uses a simple token approach (no JWT, no HMAC):

- Format:
```
<userId>:<role>:<derivedUuid>
```
- Where:
  - `<userId>` — user's UUID string
  - `<role>` — user's role string (e.g. ADMIN, CUSTOMER)
  - `<derivedUuid>` — deterministic name-based UUID derived from bytes of the string `userId:role` via `UUID.nameUUIDFromBytes(...)`.

Validation steps performed by `SimpleTokenService.validateToken`:
- Split token by `:` into 3 parts.
- Reconstruct `payload = userId + ":" + role` and compute `expected = UUID.nameUUIDFromBytes(payload.getBytes())`.
- If `expected.toString()` equals the third token part, validation succeeds and returns an `AuthPrincipal` containing the userId and role.

Note: this deterministic token can be forged by anyone who knows a valid userId and role — there is no secret or signature.


## Why not JWT / why simple tokens?

You asked explicitly to avoid JWT and Bearer tokens; the system follows a deliberately simple approach:
- Quick to implement and easy to inspect.
- Works for trusted internal environments and development/testing convenience.
- Drawback: without a secret or signing, tokens are not forgery-resistant.

A more secure alternative (already present earlier in the codebase but removed on request) used HMAC with a secret and timestamp.


## Headers summary

- `X-Auth-Token` (preferred): the token returned from authentication; filter validates it by `TokenService`.
- `X-User-Id` (dev/test fallback): the user UUID string; filter looks up the user entity and applies its role.

Usage examples (curl):

Authenticate (get token):

```bash
curl -s -X POST -H "Content-Type: application/json" \
  -d '{"email":"alice@example.com","password":"secret"}' \
  http://localhost:8080/api/auth/authenticate
```

Call protected endpoint using token:

```bash
curl -H "X-Auth-Token: <token-from-auth>" http://localhost:8080/api/orders
```

Dev-only: call protected endpoint using `X-User-Id`:

```bash
curl -H "X-User-Id: 123e4567-e89b-12d3-a456-426614174000" http://localhost:8080/api/orders
```


## Configuration

There are no required properties for the simple token mode. If you switch to a signed token implementation later, configure secrets in `application.yaml` or environment variables.

Recommended configuration keys (if you later enable a signed token service):

```yaml
app:
  auth:
    token-secret: "<strong-secret>"
    token-expiry-seconds: 86400
    allow-impersonation: false   # whether X-User-Id is accepted (recommend false for prod)
```


## Security notes and recommended changes

The current simple-token approach is insecure for public production use. Recommended options:

1. Enable signed tokens (HMAC) with expiry.
   - Use a secret stored in environment variables or a secrets manager.
   - Validate signature and expiry in the token service.
2. Disable or guard `X-User-Id` in production.
   - Add `app.auth.allow-impersonation` property and check it in `SimpleAuthFilter`.
   - Or require an additional internal-only header (gateway-injected) to accept `X-User-Id`.
3. Add monitoring and logging:
   - Log and rate-limit invalid token attempts.
   - Alert on repeated failed attempts (possible attack).
4. Add tests and integration checks for token generation and filter behavior.


## How to switch to a secure token (quick steps)

1. Implement a `TokenService` that signs tokens using HMAC-SHA256 with a server secret and includes a timestamp. (An HMAC-based implementation existed earlier in repo history.)
2. Register that service as the primary `TokenService` bean (e.g., annotate with `@Primary` or remove `@Primary` from `SimpleTokenService`).
3. Add `app.auth.token-secret` in `application.yaml` (env var recommended) and `app.auth.token-expiry-seconds`.
4. Update docs and clients to continue sending tokens in `X-Auth-Token`.

## FAQs

Q: Why `X-Auth-Token` instead of Authorization: Bearer?
- You asked not to use Bearer/JWT. The system uses a custom header `X-Auth-Token` for the simple token approach.

Q: What if I want to revoke tokens?
- With the stateless simple token, revocation isn't directly supported. Use a signed token with a token-id stored server-side or maintain a revocation list.

Q: Where can I see which user is authenticated in code?
- Read from MDC (Mapped Diagnostic Context): `MDC.get("userId")` and `MDC.get("userRole")`. Some project aspects and controllers read these values for logging and authorization.
